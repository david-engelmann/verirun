## Findings raised by the programme

### PF-1. Directory entry durability is weaker on Windows

Raised in W4. Unix syncs the destination directory after the rename, so a reported success means the entry itself is durable. Windows offers no directory sync, and the put protocol's answer there is the write-through rename, the strongest ordering the platform gives for an entry. A crash can still lose the newest entry on Windows where the Unix sequence would keep it. The consequence is bounded by the store's own rules, because every read rehashes what it returns, so a lost entry reads as a missing object and never as corrupt data, and a missing object is a retry and not a wrong answer. The pin path carries the same residual with no rename mitigation at all, because pins are created in place, so a crash can drop a pin whose creation already returned success, and that loss reads as an unpinned manifest at the next collection rather than as a retry. The disposition is to accept the difference as a recorded platform fact, with the mapping written into section 6.2 of the architecture document. The finding reopens if a future Windows primitive offers directory level ordering.

### PF-2. Executable resolution returns an untyped error

Raised and rejected in P2. The runner's executable resolution returns a plain `String` error where every other public surface in the workspace returns a typed one. The rejection rests on the string being the contract, because it is recorded verbatim as the execution's failure detail in the manifest, no caller anywhere branches on the failure kind, and a typed form would break a public method only for every consumer to render it back into the same string.

### PF-3. Three identical `make_writable` helpers in the CLI test fixtures

Raised and rejected in P4. The CLI suites `cli_diff`, `cli_exit_codes`, and `cli_show` each carry a byte identical `make_writable` helper, fifteen lines encoding how a stored object is made writable in the platform's own terms. Unlike the variants the audit programme counted for F22, these three do not differ. The rejection rests on the structure they sit in, because each integration test file is its own crate and the per file helper is the test structure this repo uses throughout, twenty suites and more, and sharing these three would take a path shared module the repo has avoided everywhere or a test support crate with a publish surface of its own. The idiom they encode has changed once, when W6 created it, and the windows CI job runs all three suites, so a missed copy would fail loudly rather than drift silently.

### PF-4. Three traceability rows named tests that did not exist

Raised and landed in P6. A mechanical check of the INVARIANTS traceability matrix against the tree, every named test searched by name in its named file, found three of the 82 named tests existing nowhere in the test estate. The integer out of range case for `INV-CAN-3`, the duplicate env key case for `INV-CAN-7`, and the relocated store verify that was `INV-MAN-2`'s only named test. All three are written in P6 under the exact names the matrix already carried, and two matrix rows that named their files inexactly now name the CLI test files exactly. The check also confirmed the rest of the matrix resolves, and that the tree carries zero ignored tests.

### PF-5. Section 8 of the architecture tells one platform's story in three passages

Raised and landed in P8. The section opens by promising that where a mechanism differs by platform the text names both, and three of its passages describe the pre-W world instead. The 8.3 timeout bullet names only the Unix group kill and never the job object. The 8.2 paragraph on `PATHEXT` resolution sits fused into the section heading itself. Rule 5 of 8.4 describes materialization as following the same component walk, pointing at a rule 4 that has described handle traversal since W3, while materialization keeps its own metadata walk. All three passages are rewritten in P8 to the two platform reality the code implements.

### PF-6. The durable rename's name promises more than the Unix function does

Raised in P9 and landed in P12 for `0.2.0` publication. The seam's rename was called `rename_durable` on both platforms. On Windows the name was literal because the call passes `MOVEFILE_REPLACE_EXISTING` and `MOVEFILE_WRITE_THROUGH`. On Unix the function is an atomic `rename`, and directory-entry durability arrives from the caller's parent-directory `sync_all` after it returns. Because `verirun-platform` publishes in `0.2.0` where outside readers meet the function directly, P12 renames it to `verirun_platform::rename_replace` across `verirun-platform`, `verirun-store`, tests, and documentation, stating both platform contracts explicitly.

### PF-7. The full CI jobs duplicate their step lists

Rejected in P11. Since W7 the `windows` job (and from P13 the `macos` job) mirrors the `rust` job's step list line for line across format, clippy, test, docs, examples, and benches, and the lists must be kept in step by hand. The candidate was to unify them by matrix or shared workflow, and it is rejected on the evidence of W7's own history. The jobs differ in a load-bearing policy a shared shape would hide, because the case count rule is 1000 on pull requests and 10000 on main for the `rust` job while `macos` and `windows` run 1000 on pull requests and 100 on pushes and merge groups, a measured decision from the W7 probe rather than an accident to be tidied away. The duplication is declarative, sits in one file where a diff shows every list at once, and fails loudly in CI itself if any list drifts. Any step change lands in all full-gate jobs in the same change, and this entry is the standing reminder.

### PF-8. The Windows traversal error carries an unrecognized NTSTATUS code as hex text

Rejected in P12. The platform seam's Windows backend maps unrecognized `NTSTATUS` values to an `io::Error` carrying the status code's hex text, whereas the Unix backend preserves the raw OS errno. Unifying them was rejected because no downstream caller branches on the inner `io::ErrorKind`, `std::io::Error::from_raw_os_error` on Windows expects Win32 error codes rather than `NTSTATUS` values so hex text is the faithful lossless diagnostic, and all contract-relevant statuses (missing, link, and non-regular file) are already mapped to explicit `TraversalError` variants on both platforms before reaching the fallback path.

## Workstream records

### W1. The Windows runner core

The runner now compiles and runs on Windows. Process control goes through a new internal crate, `verirun-platform`, which holds the workspace's only unsafe blocks behind a safe `ProcessGroup` API. On Unix the child leads its own process group and termination signals the group. On Windows the group is a job object created with kill on job close, assigned the child immediately after spawn, and terminated as a whole at the deadline. Executable resolution on Windows applies the `PATHEXT` snapshot to bare names and treats the executable extensions as the executable test, where Unix uses permission bits. A portable runner test suite proves exit codes, the hermetic environment, byte exact capture, and whole tree termination with the same test text on both platforms, and the Windows CI job runs it. Two consequences are recorded. The platform crate is a fourth workspace crate and a dependency of the store crate, so the next release publishes it alongside the existing three. Assignment immediately after spawn leaves a narrow window in which a child could spawn a process outside the job, the same class the Unix group has always had with session creation, and the drain grace bounds its cost.

The first hosted run of the portable suite failed all four tests, and a staged probe on a throwaway branch isolated the failure below the runner, in the store, where the seam attached and terminated cleanly, resolution worked, and execution died inside the put protocol. Two Windows file semantics differences in the put's final step are fixed in this slice because its gate cannot pass without them, and both are recorded here rather than smoothed over. First, the rename at the end of a put raced a concurrent put of the same digest, where the presence check passed for both, the winner set the object read-only, and the loser's rename was refused because Windows will not replace a read-only file where Unix replaces identical bytes silently. A failed rename whose destination now exists completes the way the discard path does, syncs and phases included. Second, directory sync has no Windows equivalent, so the step is a no-op there in this slice. That is a real durability difference, and it is carried to W4, whose slice re-proves this protocol under Windows file semantics and writes the mapping down.

With those two fixes in, three of the four portable tests pass on Windows and the runner itself probes clean end to end. The remaining failure was the hermetic environment test's expectation rather than the runner, because a staged dump of the environment inside a task showed the runner's five pairs plus three variables `cmd` synthesizes for itself when they are absent (its own path, its extension list, and its prompt). The test removes those three on Windows before its exact comparison, matching the Unix side running `env` directly rather than a shell, so the comparison stays exact over everything the runner controls.

### W2. Pipes, draining, and timeout parity

The drain machinery was already platform neutral, so this slice adds its gate evidence to the portable suite and changes no production code. The volume case runs eight mebibytes on each stream in one task with both streams in flight together and asserts the captured blobs byte for byte against patterns built in process. The timeout case has the child write a known prefix, flush it, and sleep holding both pipes, so the captured stream equals the prefix. A third case, Unix only, detaches a writer that escapes the tree kill, so the ten second drain grace and the stream cutoff are exercised directly and the finalized stream is an exact prefix of the endless stream with the cut noted. Windows children cannot break out of their job object, so on Windows the grace parity rests on the shared collection code and the prefix case, and this entry states that plainly rather than claiming a Windows cutoff run. One contract fact fell out of the Windows diagnosis. A PowerShell child cannot start under the runner's hermetic environment unless the spec declares `SystemRoot`, because the interpreter loads its managed runtime from the system root. The portable cases declare it, and a spec that runs interpreter children on Windows must do the same. Hosted evidence comes from this slice's pull request CI, whose `windows` job and `rust` job both ran green on the merged head.

### W3. Sandbox, collection, and the F11 window

Collection no longer walks a declared output by path and opens it afterwards. The platform seam grew a second safe API, a directory handle that opens one component at a time relative to itself, descriptor relative through `openat` with no-follow semantics on Unix and handle relative through the native create call with reparse point inspection on Windows. The runner's collection opens every declared output through that traversal and streams the opened file into the store, so the file checked is the file read, and a component swapped between a check and an open has nothing to redirect. Carried item C2 and audit finding F11 close on this slice. The gate evidence is the `traversal` suite in the platform crate, whose race case flips a component between a real directory and a link to a decoy tree while traversals run and asserts the decoy's bytes are never collected, plus the portable suite's nested collection and linked component cases, running green on both platforms in CI.

### W4. Store durability on Windows file semantics

The put protocol now renames through the platform seam, where the Windows rename is the native move call with the replace and write-through flags, so the rename itself carries the strongest ordering the platform offers for a directory entry. File sync was already the platform flush through the standard library. Directory sync stays a no-op call on Windows because no equivalent exists, and section 6.2 of the architecture document maps every protocol step to its Windows counterpart with the residual difference named. Two latent defects fell out of reading the removal sites. A put's temp file carries the read-only attribute by the time the discard paths remove it, and the collector removes read-only objects with a plain delete, and Windows refuses both, so stored file removals now clear the attribute and retry once when a read-only file refuses. The discard path is pinned by a deterministic fault test that lands the same bytes through a second store handle mid put. The directory entry difference is recorded as finding PF-1, not smoothed over. Hosted evidence comes from this slice's pull request CI on Linux and Windows.

### W5. Scheduler parity and the identity proof

The tamper suite's object overwriting sets permissions in the platform's own terms, mode bits on Unix and the read only attribute on Windows. The Windows CI job runs the crash recovery suite, the tamper suite, and the identity suite beside the fault suite.
