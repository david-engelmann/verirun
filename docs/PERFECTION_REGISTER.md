## Findings raised by the programme

### PF-1. Directory entry durability is weaker on Windows

Raised in W4. Unix syncs the destination directory after the rename, so a reported success means the entry itself is durable. Windows offers no directory sync, and the put protocol's answer there is the write-through rename, the strongest ordering the platform gives for an entry. A crash can still lose the newest entry on Windows where the Unix sequence would keep it. The consequence is bounded by the store's own rules, because every read rehashes what it returns, so a lost entry reads as a missing object and never as corrupt data, and a missing object is a retry and not a wrong answer. The pin path carries the same residual with no rename mitigation at all, because pins are created in place, so a crash can drop a pin whose creation already returned success, and that loss reads as an unpinned manifest at the next collection rather than as a retry. The disposition is to accept the difference as a recorded platform fact, with the mapping written into section 6.2 of the architecture document. The finding reopens if a future Windows primitive offers directory level ordering.

### PF-2. Executable resolution returns an untyped error

Raised and rejected in P2. The runner's executable resolution returns a plain String error where every other public surface in the workspace returns a typed one. The rejection rests on the string being the contract, because it is recorded verbatim as the execution's failure detail in the manifest, no caller anywhere branches on the failure kind, and a typed form would break a public method only for every consumer to render it back into the same string.
### PF-3. Three identical make_writable helpers in the CLI test fixtures

Raised and rejected in P4. The CLI suites cli_diff, cli_exit_codes, and cli_show each carry a byte identical make_writable helper, fifteen lines encoding how a stored object is made writable in the platform's own terms. Unlike the variants the audit programme counted for F22, these three do not differ. The rejection rests on the structure they sit in, because each integration test file is its own crate and the per file helper is the test structure this repo uses throughout, twenty suites and more, and sharing these three would take a path shared module the repo has avoided everywhere or a test support crate with a publish surface of its own. The idiom they encode has changed exactly once, when W6 created it, and the windows CI job runs all three suites, so a missed copy would fail loudly rather than drift silently.
### PF-4. Three traceability rows named tests that did not exist

Raised and landed in P6. A mechanical check of the INVARIANTS traceability matrix against the tree, every named test searched by name in its named file, found three of the 82 named tests existing nowhere in the test estate. The integer out of range case for INV-CAN-3, the duplicate env key case for INV-CAN-7, and the relocated store verify that was INV-MAN-2's only named test. All three are written in P6 under the exact names the matrix already carried, and two matrix rows that named their files inexactly now name the CLI test files exactly. The check also confirmed the rest of the matrix resolves, and that the tree carries zero ignored tests.
### PF-5. Section 8 of the architecture tells one platform's story in three passages

Raised and landed in P8. The section opens by promising that where a mechanism differs by platform the text names both, and three of its passages describe the pre-W world instead. The 8.3 timeout bullet names only the Unix group kill and never the job object. The 8.2 paragraph on PATHEXT resolution sits fused into the section heading itself. Rule 5 of 8.4 describes materialization as following the same component walk, pointing at a rule 4 that has described handle traversal since W3, while materialization keeps its own metadata walk. All three passages are rewritten in P8 to the two platform reality the code implements.
### PF-6. The durable rename's name promises more than the Unix function does

Deferred in P9, to the publication decision. The seam's rename is called rename_durable on both platforms. On Windows the name is literal, because the call carries the write through flag. On Unix the function is a plain rename, and the durability arrives from the caller's directory syncs after it returns, which its doc comment states in so many words. Inside this workspace the shorthand is safe, because every caller follows the put protocol the comment points at. The platform crate publishes with the next release, and outside readers will meet the name without the protocol in front of them. The trigger for revisiting is that release's preparation, and the remedies are a rename that says replace rather than durable, or a first line reframing in the crate's own docs. Recorded now so the publication pass cannot miss it.
### PF-7. The two full CI jobs duplicate their step lists

Rejected in P11. Since W7 the windows job mirrors the rust job's step list almost line for line, format, clippy, test, docs, examples, benches, and the two lists must be kept in step by hand, which the W7 red team already flagged as a parity risk and W7's own repair then proved real when one job lacked the other's doc flags. The candidate was to unify them, by matrix or by a shared workflow. It is rejected on the evidence of that same history. The jobs differ in a load-bearing policy a shared shape would hide: the case count rule is 1000 on pull requests and 10000 on main for the rust job, and 1000 on pull requests and 100 on pushes and merge groups for the windows job, a measured decision from the W7 probe, not an accident to be tidied away. The duplication is declarative, sits in one file where a diff shows both lists at once, and fails loudly in CI itself when the lists drift, as it did in W7 and was repaired the same day. Restructuring the gate file risks the evidence machine every round in both programmes has depended on, for a tidiness gain. The parity the red team wanted is kept by the register discipline instead: any step change lands in both lists in the same PR, and this entry is the standing reminder.


## Workstream records

### W1. The Windows runner core

The runner now compiles and runs on Windows. Process control goes through a new internal crate, verirun-platform, which holds the workspace's only unsafe blocks behind a safe ProcessGroup API. On Unix the group is the mechanism the runner has always used, the child leading its own process group and termination signalling the group through the shell builtin. On Windows the group is a job object created with kill on job close, assigned the child immediately after spawn, and terminated as a whole at the deadline. Executable resolution on Windows applies the PATHEXT snapshot to bare names and treats the executable extensions as the executable test, where Unix uses permission bits. A portable runner test suite proves exit codes, the hermetic environment, byte exact capture, and whole tree termination with the same test text on both platforms, and the Windows CI job runs it. Two consequences are recorded. The platform crate is a fourth workspace crate and a dependency of the store crate, so the next release publishes it alongside the existing three. Assignment immediately after spawn leaves a narrow window in which a child could spawn a process outside the job; the window is the same class the Unix group has always had with session creation, and the drain grace bounds its cost.

The first hosted run of the portable suite failed all four tests, and a staged probe on a throwaway branch isolated the failure below the runner, in the store: the seam attached and terminated cleanly, resolution worked, and execution died inside the put protocol. Two Windows file semantics differences in the put's final step are fixed in this slice because its gate cannot pass without them, and both are recorded here rather than smoothed over. First, the rename at the end of a put raced a concurrent put of the same digest: the presence check passed for both, the winner set the object read-only, and the loser's rename was refused because Windows will not replace a read-only file where Unix replaces identical bytes silently. A failed rename whose destination now exists completes the way the discard path does, syncs and phases included. Second, directory sync has no Windows equivalent, so the step is a no-op there in this slice. That is a real durability difference, and it is carried to W4, whose slice re-proves this protocol under Windows file semantics and writes the mapping down.

With those two fixes in, three of the four portable tests pass on Windows and the runner itself probes clean end to end. The remaining failure is the hermetic environment test's expectation, not the runner: a staged dump of the environment inside a task shows exactly the runner's five pairs, plus three variables `cmd` synthesizes for itself when they are absent (its own path, its extension list, and its prompt). The test now removes those three on Windows before its exact comparison, the same shell bookkeeping that makes the Unix side run the `env` program directly rather than a shell, so the comparison stays exact over everything the runner controls.

### W2. Pipes, draining, and timeout parity

The drain machinery was already platform neutral, so this slice adds its gate evidence to the portable suite and changes no production code. The volume case runs eight mebibytes on each stream in one task with both streams in flight together and asserts the captured blobs byte for byte against patterns built in process. The timeout case has the child write a known prefix, flush it, and sleep holding both pipes; the captured stream equals exactly the prefix. A third case, Unix only, detaches a writer that escapes the tree kill, so the ten second drain grace and the stream cutoff are exercised directly and the finalized stream is an exact prefix of the endless stream with the cut noted. Windows children cannot break out of their job object, so on Windows the grace parity rests on the shared collection code and the prefix case, and this entry states that plainly rather than claiming a Windows cutoff run. One contract fact fell out of the windows diagnosis. A PowerShell child cannot start under the runner's hermetic environment unless the spec declares SystemRoot, because the interpreter loads its managed runtime from the system root. The portable cases declare it, and a spec that runs interpreter children on Windows must do the same. Hosted evidence: this slice's own pull request CI, whose windows job runs the grown portable suite on windows-latest and whose rust job runs it inside the full workspace suite, both green on the merged head. No production difference was forced by the evidence.

### W3. Sandbox, collection, and the F11 window

Collection no longer walks a declared output by path and opens it afterwards. The platform seam grew a second safe API, a directory handle that opens one component at a time relative to itself, descriptor relative through openat with no-follow semantics on Unix and handle relative through the native create call with reparse point inspection on Windows. The runner's collection opens every declared output through that traversal and streams the opened file into the store, so the file checked is the file read, and a component swapped between a check and an open has nothing to redirect. Carried item C2 and audit finding F11 close on this slice. The gate evidence is the traversal suite in the platform crate, whose race case flips a component between a real directory and a link to a decoy tree while traversals run and asserts the decoy's bytes are never collected, plus the portable suite's nested collection and linked component cases, running on both platforms. Hosted evidence: this slice's own pull request CI, whose windows job runs the traversal and portable suites on windows-latest and whose rust job runs them inside the full workspace suite, both green on the merged head.

### W4. Store durability on Windows file semantics

The put protocol now renames through the platform seam, where the Windows rename is the native move call with the replace and write-through flags, so the rename itself carries the strongest ordering the platform offers for a directory entry. File sync was already the platform flush through the standard library. Directory sync stays a no-op call on Windows because no equivalent exists, and section 6.2 of the architecture document now maps every protocol step to its Windows counterpart with the residual difference named. Two latent defects fell out of reading the removal sites. A put's temp file carries the read-only attribute by the time the discard paths remove it, and the collector removes read-only objects with a plain delete, and Windows refuses both, so stored file removals now clear the attribute and retry once when a read-only file refuses. The discard path is pinned by a deterministic fault test that lands the same bytes through a second store handle mid put. The directory entry difference is recorded as finding PF-1, not smoothed over. Hosted evidence: this slice's own pull request CI, whose windows job runs the fault suite on windows-latest and whose rust job runs it inside the full workspace suite, both green on the merged head. The crash recovery suite imports the scheduler, so it joins the windows job in W5 with scheduler parity, and the cross device refusal at store open stays a Unix device id check with its fault test fenced to Unix. The tamper suite is bound the same way as the crash recovery suite, importing the scheduler and a Unix permissions API, so it joins the windows job on the same schedule.

### P3. Performance, first cycle
